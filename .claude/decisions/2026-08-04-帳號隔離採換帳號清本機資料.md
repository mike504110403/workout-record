# 帳號隔離:換帳號清本機資料(2026-08-04)

## 背景

波 1 review(2026-07-30)揪出:登出/換帳號只清 prefs,Drift 資料完全沒隔離——repositories 全表查詢無 userId 過濾,換一個 Apple ID 登入後,波 2+ 的資料頁會直接看到前一個人的訓練紀錄;血緣裝置上新帳號還會被綁到前人的 user row。同步波前本機 Drift 是唯一資料源,必須先定隔離模型才能開資料頁波次。

## 選項

- **A. 全查詢帶 userId**:多帳號資料共存本機,所有 repository 查詢/寫入都加 userId 過濾。改造面大(7 個 repository + 既有測試),且與「單使用者 App」的產品現實不符。
- **B. 換帳號清本機資料**:本機 Drift 永遠只屬於一個帳號;偵測到不同帳號登入即清空本機資料重新開始。repository 層零改動;共用裝置多帳號是邊緣情境,同步波後資料在雲端、換帳號拉自己的即可。

## 選擇

**B(Mike 2026-08-04 拍板)。**

## 理由與實作要點

- 與 CoreData 舊版單使用者模型一致;repository 查詢層不用全面改造;同步波的伺服器端本來就以帳號為界,本機只是快取。
- 實作:prefs 記 `local_data_owner_user_id`(本機資料擁有者)。登入成功時:無 owner → 認領(寫入);owner == 自己 → 照常;owner != 自己 → **警告對話框二次確認**後清 Drift 全表 + Onboarding 個資 prefs + onboarding 旗標,再認領。隱私同意三 key 是裝置層級,不清。
- 血緣 key `coredata_imported_user_id` 隨首次認領一次性消耗(security review 2026-07-30 建議):首個登入帳號認領匯入資料後,該 key 的血緣判斷讓位給 owner 機制。

## 實作補充(2026-08-04 波 2 review 後定)

- 清空全表後於同一交易**重種系統動作庫**(`isSystem` 參照資料,非帳號個資)——不重種等同新帳號動作庫全空。
- 血緣 key 的「一次性消耗」實作為**換帳號確認清除時移除**(非字面的首次認領當下):首個認領帳號在其為 owner 期間持續享有血緣行為;不變式維持——後續帳號永不綁前人 Users row。
- 確認清除同時**退休裝置層匯入**:CoreData 匯入完成旗標設 true、失敗旗標與重試次數歸零、legacy prefs 匯入旗標設 true——否則重啟後匯入器會把前人歷史還原給新帳號(security review 2026-08-04 major)。
